# 設計書生成ガイド（`/aidlc --doc`）

`/aidlc --doc`（KDDI ハーネスから移植した D の Claude 拡張）が、各ステージ成果物を**読んで解釈・統合した設計書群**を
**space-level** の `aidlc/spaces/<active-space>/design-document/` に生成するための方法論。
生成は LLM が行う（決定論ツールではない）。
**システム化構想・基本設計・詳細設計の3層をディレクトリで分け**、各層を**機能要件・非機能要件で一般に
整備すべき観点を網羅した固定の章立て**（後述の標準章立てテンプレート）に沿ったトピック別ファイルに
分割する。システム化構想より前に置く **`00_設計管理/`** に**要件一覧（要件番号・優先度付き）**・**状態×イベントの網羅
マトリクスと抜け（要確認）検出**・**トレーサビリティ**・**用語集**・**設計判断記録（ADR）**・
**リスクと技術的負債**・**未検討一覧**・**未決定事項管理表**を置く。詳細設計は Web アプリ / API /
バッチ / DB / インフラの**コンポーネント種別**ごとに分ける。

品質目標は「AI-DLC 成果物のリンク集」ではなく、KDDI の業務仕様書としてそのままレビューできる粒度。
各章は原典を開かなくてもレビューできる**噛み砕いた解釈**にする。参考スタイルは、KDDI 案件で使われる
次の型である:

- README/全体像: 読み方、ファイル構成、ID体系、ステータス定義、参照元、変更点、ブロッカー現在地。
- 要件詳細: `REQ-<domain>-NNN` などの ID ごとに、内容・対象/対象外・根拠・優先度・ステータス・未決事項を
  明示。
- マトリクス集: ユーザ状態 × 機能、状態×イベント、エラー × 応答コード、システム × 変更種別、IF/API × 要件。
- 未決定事項管理表: `D-<domain>-NNN` の ID、論点、状態、担当/確認先、関連要件、次アクション。
- トレーサビリティ: 要件 → 出典 → 画面/状態 → IF/API/システム → 実装/テストの往復参照。
- 図: 状態遷移、画面遷移、シーケンス、業務/処理フロー、システム構成を Mermaid で表現する。
  **状態とイベントが揃う箇所は網羅的に図・表へ落とし、表だけで終わらせない**（詳細は後述の
  「図の生成ルール」節）。

## 位置づけと不変条件（classification）

- **workflow state に対して read-only**: stage ポインタを進めない。audit イベントを emit しない。
  `aidlc-state.md` / audit シャードを変更しない。書き込みは設計書ルート配下のみ。
- **正本は各ステージ成果物**。本設計書群はそれらを解釈・統合した二次文書であり、既定
  （incremental）では既存 `design-document/` を読んで差分を統合し、`--full` 指定時のみ
  毎回ゼロから上書き再生成する（古いフラット形式が残っていれば `--full` で作り直す。
  詳細は後述「incremental（既定）と `--full`」節）。
- **解釈はする、捏造はしない**: 散文へ噛み砕き、横断して統合してよい。ただし要件・要件番号・画面・
  ギャップは必ず元成果物に trace し、原典に無いものを事実として書かない。不明は「要確認」とする。
- **薄い要約で終わらせない**: 各章は、原典を開かなくてもレビュー会で議論できる具体度にする。
  単なる「〜を生成する」「〜を確認する」ではなく、誰/何/どの状態/どの画面/どのIF/どの例外に効くかを書く。
- **決定と未決を分ける**: 決定済み・暫定・方向性判明・未確定・対象外/将来フェーズを混ぜない。
  未確定は本文に埋めず、要確認・未決定事項・未検討として ID 付き／マーカー付きで表面化する。
- **網羅の形を崩さない**: 後述の標準章立ての章は、内容が無くても削除しない。空なら「未検討」を残す。
  これは既存章・新設章を問わず**一切の例外なく**適用する固定ルールである（詳しくは後述の
  「標準章立てテンプレートと未検討マーカー」節）。

## ロケール

本文・層名（システム化構想 等）・見出し・マトリクスの見出しは**日本語**。

設計書は KDDI 業務レビューでそのまま使う成果物なので、**ディレクトリ名・ファイル名も日本語**にする
（参照docの体裁に合わせる。例: `01_システム化構想/01_全体像.md`、`00_設計管理/要件一覧.md`）。これは
**read-only な二次成果物で、sensor・決定論エンジン・既存テストが構造を読まない**ための、ハーネス
全体の「構造＝英語」規約に対する**意図的な局所例外**である。一方、次は英語のまま保つ:
要件 ID・画面/Section ID・状態ID（`FR-point-052`, `NFR-point-001`, `US-3`, `SCR-001`, `S-08`, `M5` など）、
見出し anchor 内のコード識別子、パス中のコマンド・コード識別子（`aidlc/`, `interaction-spec.md`,
`stateDiagram-v2` など）。要件番号は成果物の実体系を優先し、別形式へ変換しない。原典に安定した要件番号が
無い場合だけ、本設計書内の管理 ID として `REQ-<domain>-NNN` を採番する（後述）。

## 入力（読む成果物）

存在するものだけを読む。代表的な配置:

- `<record>/ideation/intent-capture/`（intent-statement, stakeholder-map）
- `<record>/ideation/scope-definition/`（scope-document, intent-backlog）
- `<record>/ideation/feasibility/`, `market-research/`, `approval-handoff/`
- `<record>/inception/requirements-analysis/requirements.md`（**FR/NFR の正本**）
- `<record>/inception/user-stories/`（stories.md = US の正本, personas.md）
- `<record>/inception/refined-mockups/interaction-spec.md`（**状態・条件・画面の正本**）
  ＋ mockups.md / design-system-mapping.md / accessibility-checklist.md
- `<record>/inception/domain-design/`, `contract-design/`, `units-generation/`, `delivery-planning/`
- `<record>/construction/<unit>/{functional-design,nfr-requirements,nfr-design,infrastructure-design,code-generation}/`
- `<record>/construction/build-and-test/`, `ci-pipeline/`
- `<record>/operation/*`
- **stage artifact が明示的に引用している原典仕様**（record 外。例: `requirements.md` の
  根拠/出典列が `仕様/foo.xlsx` のような相対/絶対パスで指すサービス仕様書・対向システム仕様・
  **QA 表（Excel/CSV 等の質問回答シート）**）。`record_root` 内の成果物が明示するパスを辿る
  だけの、境界付きの参照追跡であり、盲目探索ではない（`/aidlc --doc` の入力範囲規約。正本は本節）。
  `QA#16` のような項番付き ID だけの引用、および `QA表.xlsx` のようなディレクトリを伴わない
  ファイル名だけの言及では辿らない——いずれも存在場所を解決できないため（ファイル名だけでは探索が
  必要になり、盲目探索の禁止と衝突する）。相対/絶対パスを伴うQA表への参照が見つかった場合は
  `90_QA/`（生成方法論 § 6）を生成する。

`*-questions.md` と `memory.md` は内部メモなので本文の根拠にしない（参照する場合も設計書には転記しない）。

### 基準資料（design-baseline）と改修版を使う

`doc-manifest` の `design_baselines` は space の基準資料（今リリースされている製品の画面・遷移・仕様の
書き出し一式、`aidlc/spaces/<space>/design-baseline/<name>/`）、各 intent の `baseline_copies` は
その intent の 2.5 refined-mockups で改修した写し（`<record>/inception/refined-mockups/<name>/`）と
変更一覧（`<name>-changes.json` / `.md`）。どちらかがあれば、次の章は**これを正本として**書く。
推測で画面や遷移を作り直さない。

- 画面一覧・画面遷移・ユーザーフロー・会員種別ごとの出し分け・画面仕様: 基準資料の `Screen-00`（画面一覧）、
  `Flow-00`〜`Flow-03`（遷移図・導線・画面マップ・ユーザーフロー）、`Screen-02-member`（会員種別）、
  `Spec-<画面>`（要素 el-NNN・表示状態・遷移先・API）を読む。読むときは
  `bun {{HARNESS_DIR}}/tools/ui-poc-baseline.cjs show --page <ページの絶対パス>` で中身の HTML を取り出す
  （まとめた形式のページを直接読まない）。必要な画面・図だけを読み、全ページを読み込まない。
- 改修の intent: 「現行（基準資料）→ 改修後（写し）」の形で書く。変わった画面・要素・遷移は
  `<name>-changes.json` の `screens[].elements`（el-NNN と 既存改修／新規実装／削除）と `flows` を根拠にし、
  変更要件シート `CR-*` へリンクする。変更一覧に無い変更を設計書に書かない。
- **スクリーンショット**: 設計書が扱う画面（改修した画面・新しい画面・主要な導線の画面）と、遷移図・
  ユーザーフローは、`bun {{HARNESS_DIR}}/tools/ui-poc-baseline.cjs shot --page <ページ> --out
  <design-document>/figures/<名前>.png [--width N --height N]` で撮って載せる。改修した画面は現行と改修後の
  2枚を並べる（`<画面>.before.png` / `<画面>.after.png`）。載せ方は
  `![<画面名>（現行）](figures/<名前>.png)` の直後に、元ページへのリンクと 1〜2 行の説明を置く（画像だけで
  終わらせない）。全画面は撮らない。撮れない環境（ブラウザ無し）では撮らずにリンクだけ置き、
  その旨を `未検討一覧.md` ではなく本文の注記に書く。
- 基準資料も写しも無いときは、この節は適用しない（従来どおり interaction-spec.md などから書く）。

### product-level 化と入力マニフェスト（マルチ intent）

設計書は **product-level**＝全 intent を対象にする（active intent だけではない）。上の代表パスは各 intent の
**`record_root`** からの相対位置。intent はそれぞれ自分の record を持ち、完了しても**動かない**ので、
どの intent の成果物もその場で読める（退避先という概念はない）。

全ツリーを盲目探索せず、まず入力マニフェストを取る:

```bash
bun {{HARNESS_DIR}}/tools/d-acceleration/design-document.ts doc-manifest --json --project-dir "$PWD"
```

これが `design_document_root` と、各 intent の `uuid` / `record_dir` / `record_root` /
`status` / `active` / `design_summary` / `design_summary_exists` を
決定論で列挙する。読むのはこの `record_root` 配下のみ。README の「対象 intent」表には
`record_dir`（人が読める名前）を載せる — `uuid` でも監査は通るが、散文には長すぎる。

`warnings[]` が非空なら、registry 行と record dir の対応が壊れた record が除外されている。
生成は続行してよいが、その旨を利用者に伝えて `/aidlc --doctor` を案内すること。

### 書き出し方（ファイルツールのみ）

設計書と `design-summary.md` は、**Write / Edit ツールで 1 ファイルずつ**作成・更新する。
Python・node・シェルのループやヒアドキュメントなど、生成スクリプトを書いて実行してはならない。
headless 実行（`claude -p`）には許可プロンプトに答える人がおらず、許可リストに無いスクリプト実行は
拒否されて生成が止まる。Bash で実行してよいのは、本ガイドが名指しする
`design-document.ts`（`doc-manifest` / `doc-snapshot`）だけである。

### incremental（既定）と `--full`

- `/aidlc --doc`（既定）＝ **incremental merge**: 既存 `design-document/` を読み、manifest の新規/変更 intent
  だけを再読する。各 intent は軽量な `design-summary.md` を優先し、足りない時だけ raw artifact を開く。差分を
  product-level 設計書に統合する。初回（既存設計書なし）は full 生成にフォールバック。
- `/aidlc --doc --full` ＝ 既存を無視し、全 intent の全 artifact から再生成。

**`--full` の前に必ず直前世代を退避する。** `--full` は生きた設計書を丸ごと
上書きする唯一の瞬間で、既定構成（D の `gitPersistence` 無効・`aidlc/` 未コミット）では他に復旧手段が無い。

```bash
bun {{HARNESS_DIR}}/tools/d-acceleration/design-document.ts doc-snapshot --project-dir "$PWD"
```

退避先は space-level の `aidlc/spaces/<space>/intents/.aidlc-d-doc-snapshot/`（**1 世代のみ**・実行の
たびに置換・gitignore 済み）。設計書が空/未生成なら既存スナップショットを保持したまま no-op で
報告する。**退避が失敗（非ゼロ exit）したら `--full` を実行せず**、エラーを利用者に見せて指示を
仰ぐこと。誤って上書きした場合の復旧はツールの出力が示す `cp -R` 一行で行える。
incremental（既定）では実行しない — 差分統合は破壊的でないため。

### design-summary（任意・incremental の燃料）

各 intent の `design-summary.md`（追加/変更要件 ID・影響画面/コンポーネント・決定/ADR・リスク）を置くと、
incremental が全 artifact ではなく digest を読める。manifest の `design_summary_exists: false` の intent には、
その `design_summary` パス（manifest が intent ごとに示す `<record_root>/design-summary.md`）に
生成時に書いてよい（設計書ルート以外で唯一許される書き込み先）。

### 要件番号とトレーサビリティ

要件番号は作成してよい。ただし、**要件そのものを作るのではなく、原典から抽出した要件を追跡するための
管理 ID を付ける**という扱いにする。

- `requirements.md` / `stories.md` に `FR-...` / `NFR-...` / `US-...` などの安定 ID がある場合:
  その ID を正本としてそのまま使う。別形式へ変換しない。
- 原典に明確な要件はあるが安定 ID が無い場合:
  `REQ-<domain>-NNN` を本設計書内の管理 ID として採番する。採番した行には `採番元` / `出典パス` /
  `原典見出し` / `原典抜粋または要約` を必ず持たせ、後から原典へ戻れるようにする。
- 原典に無い要件は追加しない。新しい要件に見えるものは `要確認` または `未決定事項管理表.md` に置き、
  要件一覧へ確定要件として混ぜない。
- `REQ-<domain>-NNN` は**設計書内の管理 ID**であり、上流のステージ成果物（requirements.md、
  refined-mockups の各成果物など）へは書き戻さない。

このため、`00_設計管理/要件一覧.md` が要件 ID の正本一覧になり、`00_設計管理/トレーサビリティ.md` が
要件 ID から出典・設計・実装・テストへ戻る往復参照を持つ。各章の本文はこの ID を参照し、同じ要件を
章ごとに別採番しない。

## 出力構成（`aidlc/spaces/<active-space>/design-document/`）

既定（incremental）では既存の `design-document/` を読んで差分を統合し、`--full` 指定時のみ
毎回ゼロから作り直す（前述「incremental（既定）と `--full`」節）。下のツリーは**アプリ系（フル）の例**。scope により
骨格そのものが変わる（後述「標準章立てテンプレート § アーキタイプの判定」で A〜D を切り替える）。
どのアーキタイプも **表紙 ＋ 設計管理ディレクトリ** を持ち、各 .md は標準章立ての章を過不足なく持つ。
内容が無い章は「未検討」を残す（後述の graceful degradation）。

```
design-document/
  README.md                       # 表紙・読み方・ファイル構成・ID体系・ステータス定義・参照元・カバレッジ・ブロッカー現在地
  table-width.css                 # Markdown プレビューでテーブルを全幅表示する補助CSS（骨格外・常に生成）
  figures/                        # 基準資料・改修版の画面と遷移図のスクリーンショット（ui-poc-baseline.cjs shot。基準資料があるときだけ）
  00_設計管理/
    要件一覧.md                   # 要件一覧（FR / NFR / US / REQ を番号付きで集約、優先度/ステータス/根拠付き）
    状態イベントマトリクス.md      # 状態×イベント/ユーザ状態×機能/エラー×応答の網羅マトリクス＋抜け（要確認）
    トレーサビリティ.md            # 要件番号 × 出典 × 画面/状態 × IF/API/実装/テスト＋カバレッジ＋逆引き
    用語集.md                     # ドメイン用語・略語の定義（Glossary）
    設計判断記録.md                # 主要な設計判断と理由（ADR 索引。リポジトリ adr/ を参照・要約）
    リスクと技術的負債.md          # 優先度付きリスク・技術的負債と緩和策
    未検討一覧.md                 # 標準章立てのうち「未検討／対象外」の章を全 .md 横断で集約（観点カバレッジ）
    未決定事項管理表.md            # D-<domain>-NNN（論点・状態・影響範囲・関連要件・根拠・次アクション）
  01_システム化構想/
    01_全体像.md                  # 背景・現状/課題/目的・ゴール/あるべき姿/対象範囲/ステークホルダー
    02_業務フロー.md              # As-Is/To-Be 業務フロー/業務シナリオ/業務上の例外・代替フロー
    03_システム全体像.md          # システム化範囲/全体構成/関連システム・外部連携の俯瞰/全体方式
    04_要求概要・実現方式.md      # 要求概要(業務/機能/非機能要求の概要)/実現方式候補(複数案比較)
    05_効果・リスク・方針.md      # 効果・価値(KPI含む)/リスク・制約/推奨方針/次工程への申し送り
  02_基本設計/
    01_システム概要.md            # 目的/基本設計時点の対象範囲・対象外/前提条件/関連文書/用語/要求一覧サマリ
    02_業務・利用シーン.md        # 利用者/業務フロー(詳細ステップ)/ユースケース一覧(UC-ID)/例外ケース/業務ルール
    03_機能設計.md                # 機能一覧/機能要件詳細(噛み砕いた解釈)/業務ルール・計算ロジック
    04_画面設計.md                # 画面一覧/画面遷移/レイアウト方針/UI表示状態(primary-state/modal等)/入力チェック
    05_外部インターフェース設計.md  # 外部IF一覧/連携方式・タイミング/連携データ概要
    06_帳票・バッチ設計.md         # 帳票一覧・出力条件/バッチ・ジョブ一覧・起動契機・処理概要
    07_データ設計.md               # 論理データモデル/コード設計/データ移行方針
    08_状態・ライフサイクル設計.md # 業務エンティティ(申請/注文/契約等)の状態一覧/状態遷移/遷移条件/操作可能者/履歴/取消・例外
    09_エラー・メッセージ設計.md   # エラー分類/エラー・例外仕様/復旧方針/メッセージ設計/通知・メール/ログ方針
```

## 標準章立てテンプレートと未検討マーカー

設計書は「書ける所だけ書く」のではなく、**機能要件・非機能要件で一般に整備すべき観点を網羅した
固定の章立て**を常に持つ。各 .md ファイルは下表の章（`##` 見出し）を**過不足なく**持ち、各章は
次のいずれかで必ず本文に現れる:

- **記載**: 成果物から内容が導ける → 噛み砕いて記載する（根拠IDを併記）。
- **未検討**: まだ検討されていない／成果物に根拠が無い → 章見出しは残し、本文を次の形にする:
  > 未検討（理由: <なぜ今は無いか> ／ 確定先: <どの stage・成果物で埋まる見込みか>）
  空欄のまま削除しない。これにより「この観点はまだ検討されていない」事実が設計書に残る。
- **対象外**: 案件として明確に範囲外 → `対象外（理由）` と書き、未検討と区別する。

成果物に新たな観点が現れたら章を増やしてよいが、表の章は省略しない。未検討・対象外の章は
`00_設計管理/未検討一覧.md` に全 .md 横断で集約し、`README.md` のカバレッジにも件数を出す。
基本設計着手・実装着手の妨げになる未検討は `00_設計管理/未決定事項管理表.md` にも `D-` ID で登録する。

**この「記載／未検討／対象外」の三値ルールは、以下に記す全ての章（既存・新設・拡張を問わず）に
一切の例外なく適用する。** 新設した章（ステークホルダー・要求概要・実現方式候補・効果・価値・
リスク・制約・推奨方針・次工程への申し送り・システム概要・業務・利用シーン・状態・ライフサイクル
設計・運用設計概要・移行・リリース方針、および拡張したエラー分類・権限まわりの各項目）も、
根拠が無ければ削除せず「未検討（理由・確定先）」または「対象外（理由）」を明記する。

### アーキタイプの判定（scope による設計書タイプの調整）

生成前に active record の `aidlc-state.md` の scope（と UI の有無）から次の4アーキタイプを選び、
**そのアーキタイプ専用の章立て骨格**で生成する。重点を変えるだけでなく、骨格そのものが変わる。

| scope | UI | アーキタイプ | 骨格 |
|---|---|---|---|
| `feature` / `mvp` / `enterprise` / `workshop` / `classic` | あり | アプリ系 | A |
| `feature` / `mvp` / `enterprise` / `workshop` / `classic` | なし | API・バックエンド系 | C |
| `ui-poc-application` / `ui-poc-comparison` / `ui-poc-requirements` | — | アプリ系 | A |
| `infra` | — | インフラ系 | B |
| `poc` / `bugfix` / `refactor` / `security-patch` / `express` / `test-pro-validation` | — | 小規模・部分系 | D |

- **scope → アーキタイプの対応はこの判定表が正本。見出しには scope を列挙しない** — 出荷する
  scope は配布ごとに異なる（例: `ui-poc-*` は UI PoC プラグイン導入時のみ）ので、見出しに書くと
  配布間で章構造が食い違って見える。判定表は配布ごとに異なってよい。
- UI の有無は `interaction-spec.md` / refined-mockups の有無・画面定義の有無で判定。判別不能なら UI ありとみなす。
  ただし **`ui-poc-*` scope は UI 検出に依らず常にアーキタイプ A（アプリ系）** を選ぶ。表に無い scope は
  UI の有無で A / C を選ぶ。
- `ui-poc-requirements`（要件定義ループ）は設計・構築ステージを持たない。ラウンド（intent）を重ねて `--doc` を
  再実行すると要件・ストーリー・画面の章は育つが、基本設計・詳細設計の章は「未検討」のまま残る。それらは
  `ui-poc-application` などで設計ステージを実行した intent が加わったときに初めて埋まる。
- **どのアーキタイプでも共通**: `00_設計管理/` の章、未検討/対象外マーカー、`README.md` 表紙。骨格内では章を網羅する。
- そのアーキタイプの骨格に**含まれる**章は、該当しなくても「対象外/未検討」で残す。骨格に**含まれない**章
  （例: インフラ系に画面設計）は最初から作らない。これが「scope で設計書タイプを変える」の実体である。

##### `06_インフラ/` — リソース単位（KDDI テンプレート準拠）

`00_命名規則.md` → `01_リソース一覧.md` → サービス別ファイル（`VPC.md` / `ECS.md` / `RDS.md` /
`S3.md` / `IAM.md` / `KMS.md` / `CloudWatch.md` / `WAF.md` / `Route53.md` …）の順。

- **`00_命名規則.md` は、案件に既存の命名規則ドキュメントがあれば *そのまま転記する*（verbatim。
  要約・再構成・5行表化しない）**。命名規則は解釈する二次文書ではなく、従うべき**規約そのもの**なので、
  原文の表をそのまま写す（設計書全体の「解釈・統合」原則の例外）。探索先: `infrastructure-design`（3.4）
  成果物、プロジェクトの標準規約、リポジトリ内の terraform 命名規則 md など（複数あれば最新の正本）。
  転記した場合は冒頭に出典（ファイルパス・版）を明記する。
- **既存ソースが無い場合のみ**、下の KDDI 標準テンプレート（全セグメント表）を雛形として展開する。
  規約をフルに書き出す（要約・5行表で済ませない）。システム名/機能名の実値は `要確認` にし、
  規約構造は full に書くが固有値は捏造しない。次の順で、各セグメントを**それぞれ独立した表**にする:
  1. **ネーミングフォーマット**: `環境名-システム名-リージョン名-AWSサービス名-機能名[-AZ][-連番]`。
     AZ・連番は省略可。詳細設定で独自名が要るもの（ロール名/ポリシー名/パラメータグループ/ルール名/
     スケジュール名/タスク定義名 など）は一意名を別途付ける旨も書く。
  2. **例（分解）**: `例 / 環境名 / システム名 / リージョン名 / AWSサービス名 / 機能名 / AZ / 連番` の表で
     2〜3 行（例: `dev-oneboard-tky-alb-sp`, `stg-oneboard-tky-ecs-cluster-api`）。
  3. **環境名**: `環境 / 識別子`（商用 `prd` / ステージング `stg` / 開発 `dev` / 負荷・疑似対向 `tst`）。
  4. **システム名**: `システム・サブシステム / 識別子 / 例`（原則 3 文字略称。**プロジェクト固有**なので
     scope/intent/requirements から実値を入れ、不明なら `要確認`）。
  5. **リージョン名**: `リージョン / 識別子`（東京 `tky` など）。
  6. **AWSサービス名**: `AWSサービス / 機能 / 識別子` の**網羅表**（要約しない）。最低限、次を列挙する:
     `vpc`/`subnet`/`rt`/`eip`/`igw`/`natgw`/`peer`/`sg`/`ec2`/`ecs-cluster`/`ecs-service`/`ecs-task`/
     `ecs-role`/`ecs-cont`/`ecs-log`/`ecr`/`lambda`/`efs`/`rds`/`elc`/`s3`/`s3ap`/`alb`/`inalb`(internal ALB)/
     `nlb`/`tg`/`cf`(CloudFront)/`apigw`/`route53`/`waf`/`acm`/`kms`/`sns`/`eb`(EventBridge)/`kns`(Kinesis)/
     `backup`/`dxgw`/`sftp`/`cbd`(CodeBuild)/`cdy`(CodeDeploy)/`cct`(CodeCommit)/`ami`/`emr`。ELB は種別で分ける。
  7. **機能名**: `機能 / 識別子`（`sp`/`pc`/`afp`/`api`/`cms`/`srv`/`batch`/`dmz`/`frt`/`bak`/`cls`/`mainte`/
     `nightsleep`/`load`/`mock` など。プロジェクト固有のものは実値 or `要確認`）。
  8. **AZ**: `AZ / 識別子`（`a`/`c`/`d`、省略可）。
  9. **通番**: 同一サービス・用途・AZ が複数あり固定化が必要なときの 3 桁連番（`000`〜`999`、省略可）。
  - この標準テンプレートは**既存ソースが無いときの雛形**。後から正本の命名規則 md が現れたら、
    雛形を捨ててそれを**そのまま転記**する（雛形と正本を混ぜない）。
- **各リソースは md の表で書く（CSV にしない）**。1 リソース（または 1 サービス）= 1 ファイルで、
  列は `設定項目 / 設定項目(詳細) / 設定値 / 環境(prd/stg/dev) / 備考`。リソース名はすべて命名規則に従う。
  未確定値は `TBD（確定先）`、要検討は `要確認` と明記する（捏造しない）。
- 章は arc42 の Deployment View ＋ クラウド/セキュリティ設計（ネットワーク/IAM/データ保護/監視）の
  標準観点も満たす。
- **インフラの有無で分岐する**:
  - クラウドインフラを使う案件（infra scope、cloud リソースが計画/示唆される、infrastructure-design 成果物あり）
    → `00_命名規則.md` は上の規約をフルに書く。個々のリソースが未確定でも規約は省略しない。
  - **クラウドインフラを持たない案件**（例: ブラウザ完結・localStorage の MVP）→ 命名規則・リソース一覧は
    `対象外（理由）` とし、フォーマット 1 行の参考に留めてよい（規約のフル表は不要）。捏造で埋めない。
- インフラ系 scope（B）では `03_詳細設計/06_インフラ/` ではなく、これを主役の `02_インフラ設計/` に昇格する。

### 全アーキタイプ共通の付録（存在条件つき・骨格外）

## 生成方法論

**ファイル番号は選んだアーキタイプの章立てに従う**。本節と「図の生成ルール」で番号付きパスを
示す場合は、A（フル・画面あり）と C（API・バックエンド系）の両方で番号が変わる章を併記する。
B/D はそれぞれ専用骨格なので、該当する同名章がある場合だけ同じ生成ルールを適用する。
**番号ではなくファイル名で対応させる**——例えば「状態・ライフサイクル設計」は A では
`08_状態・ライフサイクル設計.md`、C では `07_状態・ライフサイクル設計.md` になるが、章の役割・
生成ルールは同一である。

### 0. 仕様書としての編集方針（全ファイル共通）

次の順で書く。説明の順番が重要。

1. **全体像 → 詳細 → マトリクス → 未検討/未決/トレース**の流れにする。読み手が背景を知らなくても追えるようにする。
2. 各テーブルには可能な限り **ID / ステータス / 根拠 / 関連要件** を入れる。
3. 画面・状態・IF/API・システム・テスト観点のどれかに結び付けられる情報は、本文だけで終わらせず表にする。
   **並列する項目が3件以上ある箇所（画面・ルール・契機・エラー種別・利用者種別等の列挙）は、箇条書きの
   ままにせず `項目 / 条件 / 結果または根拠` 等の列を持つ表に変換する**。単発の説明（1〜2件）や、
   表にすると逆に読みにくい単純な前提条件の説明は箇条書きのままでよい。
4. 図にすると理解が速い関係は Mermaid で表現する。原典に Mermaid が無くても、成果物から明確に導ける
   遷移・順序・責務関係なら図化してよい。推測が混じる箇所は図に入れず、未検討/未決定事項へ回す。
   **状態とイベントの両方が揃う箇所（業務エンティティのライフサイクル、複数主体が絡む業務・API連携）は、
   表だけで終わらせず必ず状態遷移図またはシーケンス図で網羅的に補う**（詳細は次項）。
5. 「未生成」「未確定」「未検討」は欠落ではなく管理対象。`00_設計管理/未検討一覧.md` と
   `00_設計管理/未決定事項管理表.md` に集約する。
6. ファイル間は相対リンクで往復できるようにする（例: `02_基本設計/03_機能設計.md` の各要件から
   `../00_設計管理/トレーサビリティ.md` の該当行へ、`README.md` から各ディレクトリへ）。

### 図の生成ルール（Mermaid）

図は飾りではなく、レビュー時に文章より早く誤りを見つけるための検査ビューとして置く。該当する入力が
存在する場合は、次を優先順で生成する。**状態を持つ対象（業務エンティティ・API リソース・画面）と、
複数主体が絡むやり取り（ユースケース・外部IF/API連携）は、表に加えて必ず図でも網羅する**。

| 図 | Mermaid | 置き場所 | 生成条件 |
|---|---|---|---|
| 業務エンティティの状態遷移図 | `stateDiagram-v2` | A: `02_基本設計/08_状態・ライフサイクル設計.md` / C: `02_基本設計/07_状態・ライフサイクル設計.md` | 申請/注文/契約/チケット等の業務エンティティの状態一覧・遷移条件が抽出できる。UIの有無を問わず生成する |
| UI表示状態の状態遷移図 | `stateDiagram-v2` | `02_基本設計/04_画面設計.md` | primary-state / modal / validation など、画面の表示・活性制御に関わる状態とイベントが抽出できる |
| 画面遷移図 | `flowchart LR` | `02_基本設計/04_画面設計.md` | Screen Registry、user-flow、操作イベントから画面/ダイアログ遷移が抽出できる |
| 業務シーケンス図 | `sequenceDiagram` | `02_基本設計/02_業務・利用シーン.md` | 利用者・承認者・システムなど複数主体が絡むユースケースの順序が抽出できる。表（UC一覧）だけで終わらせない |
| 外部IF／API連携シーケンス図 | `sequenceDiagram` | A: `02_基本設計/05_外部インターフェース設計.md` / C: `02_基本設計/04_外部インターフェース設計.md`、`03_詳細設計/03_API/<API名>.md` | 同期/非同期で複数ステップの連携がある。基本設計レベルの概要と、詳細設計レベルの API 単位仕様の両方で該当すれば生成する |
| 業務/処理フロー | `flowchart TD` | `01_システム化構想/02_業務フロー.md` または `02_基本設計/03_機能設計.md` | 業務 Step、処理順、例外分岐、補償処理が抽出できる |
| システム構成/責務 | `flowchart TB` | `01_システム化構想/03_システム全体像.md`（概要）/ `03_詳細設計/01_共通方式設計.md`・`06_インフラ/`（詳細） | 複数システム/コンポーネントと責務・データ所有が抽出できる |
| 全体像図（README 用） | `flowchart TB`（複製） | `README.md` | システム構成図が導ける場合、`03_システム全体像.md` の図を複製・要約して先頭に置く。無ければ画面遷移/状態遷移の代表図を1つ載せる |

図には次の制約をかける。

- ノード名には原典の ID（FR/US/SCR/S/M/G/D/IF/API など）を併記する。
- Mermaid の直後に `Text fallback:` コメントまたは短い箇条書きを置き、図が読めない環境でも意味が分かるようにする。
- 根拠が弱い遷移は `要確認` ノードに接続し、確定経路のように描かない。
- 状態遷移図はマトリクスと矛盾させない。マトリクスの抜け（G-N）は、図上でも `要確認` として見えるようにする。
- 図が大きくなりすぎる場合は、全体図 + 詳細図に分割する。1図に 12〜15 ノードを超えて詰め込まない。

### 1. 要件一覧と採番（`00_設計管理/要件一覧.md`）

- `requirements.md` の `## Functional Requirements` / `## Non-functional Requirements` 節にある
  要件テーブル（`| ID | 要件 | ドメイン | 優先度 | 根拠/出典 |`）の各行と合否基準、`stories.md` の `US-N` を抽出。
  ID は requirements-analysis が発番した `FR-<domain>-NNN` / `NFR-<domain>-NNN` をそのまま引く。
- 原典に安定 ID が無い要件は、設計書内管理 ID として `REQ-<domain>-NNN` を採番する。採番は
  `00_設計管理/要件一覧.md` だけで行い、各章で再採番しない。
- 番号付きテーブルにまとめる:

  | 番号 | 種別 | 優先度 | ステータス | タイトル | つまり何か | 合否基準(要約) | 採番元 | 根拠/出典 | 関連画面/状態/IF | 対応 US |
  |---|---|---|---|---|---|---|---|---|---|---|

- **優先度**（Must/Should/Could）は原典（requirements.md の優先度・重要度記述、intent-backlog 等）に
  根拠があればそれを使う。無ければ「未確認（既定 Should 扱い）」と明記し、断定しない。
- 全行を成果物へ trace する。原典に無い要件を足さない。要件番号は、原典 ID または本書上の
  `REQ-<domain>-NNN` 管理 ID のどちらかに統一する。
- requirements.md に Traceability 表（要件→上流）があれば「上流トレース」列に反映する。
- 要件をカテゴリ別に束ねる。カテゴリが原典に無ければ FR/NFR/US のまま。各要件の**噛み砕いた解釈**
  そのものは `02_基本設計/03_機能設計.md`（機能要件）/ 非機能は A: `02_基本設計/11_非機能要件.md`、
  C: `02_基本設計/10_非機能要件.md` に置き、
  ここは一覧（番号・優先度・ステータス・要約）に徹する。
- 対象外・将来フェーズ・暫定の要件は削除しない。ステータスを付け、MVP/初期スコープとの境界を明記する。
- `02_基本設計/01_システム概要.md` の「要求一覧（サマリ）」章は、この設計管理ファイルを要約・参照するのみで、
  内容を複製しない（正本はこのファイル）。

### 2. 各要件の噛み砕き（機能 → `02_基本設計/03_機能設計.md`）

各機能要件について次の形で書く:
  - **つまり**: <平易な言い換え>
  - **対象画面 / Section**: <SCR-/S- ID>
  - **状態 / 条件**: <interaction-spec の M 行や primary-state、または状態・ライフサイクル設計
    （A: `08_状態・ライフサイクル設計.md` / C: `07_状態・ライフサイクル設計.md`）の業務
    エンティティ状態、ユーザ状態、契約状態など>
  - **処理 / データ**: <登録・判定・保存・通知・集計など>
  - **例外・優先**: <エラー優先、validation 中断、入会不可、外部IF失敗など>
  - **根拠**: <requirements / stories / interaction-spec / QA / stage artifact>

### 3. 非機能要件（A: `02_基本設計/11_非機能要件.md` / C: `02_基本設計/10_非機能要件.md`）

IPA「非機能要求グレード」の 6 大分類を章に固定する（可用性 / 性能・拡張性 / 運用・保守性 / 移行性 /
セキュリティ / システム環境・エコロジー）。各分類で「設計上の意味」と「どう確認するか」を書く。
`nfr-requirements` / `nfr-design` 成果物があれば割り付け、無ければ各分類を「未検討（確定先:
nfr-requirements 3.2 / nfr-design 3.3）」で残す。性能の SLO など定量が未確定なものは未決定事項へ。

### 4. 状態×イベント網羅マトリクスと抜け検出（`00_設計管理/状態イベントマトリクス.md`）— 中核

利用者が「状態とイベントの組み合わせで、どこの使用が抜けているか」を把握するための核。
**UI の状態（画面の見た目）と業務エンティティの状態（データのライフサイクル）は別次元であり、
両方が存在する案件では両方を網羅する**（片方だけでカバレッジを語らない）。

1. **状態次元を抽出**（次の情報源を、存在するものすべて使う。どちらか一方に決め打ちしない）:
   - UI表示状態: interaction-spec から。primary-state（例: `storage-error / loading / empty / partial /
     populated`）、modal などの直交状態（例: `none / create / edit / delete-confirm / day-list`）、
     validation 等の追加フラグ（例: `valid / invalid-empty / invalid-range`）。
   - 業務エンティティの状態: 状態・ライフサイクル設計（A: `02_基本設計/08_状態・ライフサイクル設計.md` /
     C: `02_基本設計/07_状態・ライフサイクル設計.md`。無ければ functional-design の状態機械/シーケンス）から。
     例: 申請の `下書き/申請中/差戻し/承認済み/取消済み`。
   - UI が無いプロジェクトは業務エンティティの状態機械のみで構築する。状態モデルがどちらも無ければ
     「状態モデルなし」と明記して要件×シナリオの観点に切り替える。
2. **イベント／遷移を抽出**: Traceability 対応表の controls、Mermaid の辺、user-flow、
   状態・ライフサイクル設計の遷移条件から
   （例: セル選択・＋追加・予定クリック・削除・はい/いいえ・前月/次月/今日・ほか+M件・保存・Esc/キャンセル・
   承認・差戻し・取消・再申請）。
3. **マトリクスを構築**: 状態（または spec の列挙行 M0–M11 を展開）× イベント、もしくは
   `primary-state × modal × validation` の直積グリッド、または業務エンティティの `状態 × イベント`
   グリッド。spec の列挙行・Mermaid 辺と突合する。UI 以外の案件では、`ユーザ状態 × 機能可否`、
   `契約状態 × 入会/変更可否`、`エラー × 応答コード`、`システム × 変更種別`、`IF/API × 要件` のうち、
   原典に根拠がある軸を選ぶ。
4. **各セルを分類**:
   - **網羅**: spec の行（例 M5）/ Traceability 行 / Mermaid 辺 / 状態・ライフサイクル設計の
     遷移行に対応。根拠 ID を併記。
   - **意図的除外（理由付き）**: spec から導ける除外。例「loading 中は＋追加 disabled → modal は開かない」
     「modal 表示中は月移動を無効化」「承認済みの申請は再承認できない」。
   - **抜け（要確認）**: 妥当だが対応行も除外記述も無い組合せ。例「data=empty かつ modal=create
     （空月での新規作成）は M5 が populated 前提で未列挙」「差戻し状態からの取消が未定義」。
5. **出力**: マトリクス本体に続けて `## 抜け（要確認）` 一覧を置き、各項目に
   「どの状態×イベントか / なぜ抜けに見えるか / 確認すべき点」を書く。
   セル数を数えられる場合は `全セル = 網羅 + 意図的除外 + 抜け` のカバレッジを、UI状態・業務エンティティ
   状態のそれぞれについて必ず出す。抜けは `00_設計管理/未決定事項管理表.md` にも `D-<domain>-NNN` として登録する。

**反捏造**: 次元の値集合と網羅状況は spec / 状態・ライフサイクル設計から取る。積空間の推論はしてよいが、
網羅判定は spec 行を根拠に挙げる。抜けは**断定（バグ）ではなく「要確認」の問い**として提示する。

### 5. トレーサビリティ・未検討・未決定事項（`00_設計管理/`）

**`トレーサビリティ.md`**:

- `要件番号(FR/NFR/US) × {出典, 基本設計セクション, 画面/状態, IF/API/システム, 実装, テスト}` の対応表。
- 実装列は construction 成果物（`construction/<unit>/code-generation/` 等）があれば参照。無ければ
  「コード未生成（construction 前のため想定内）」と注記。
- テスト列は build-and-test 成果物や UX Acceptance Criteria（UX-AC）を参照。
- カバレッジ（例: 設計まで到達 N/全 M）と**孤立**（下流参照のない要件）を表示する。
- 逆引きも置く。例: `画面/Section → 要件`、`IF/API → 要件`、`未決事項 → 要件`、`要件 → 画面状態(M-id)`
  （M-id は interaction-spec の採番をそのまま使い、設計書側で別に採番し直さない）。

**`未検討一覧.md`**: 標準章立てのうち「未検討／対象外」となった章を全 .md 横断で集約する。

  | レベル | ファイル | 章 | 状態 | 理由 | 確定先(stage/成果物) |
  |---|---|---|---|---|---|

  記載済み章数 / 未検討章数 / 対象外章数を冒頭に出し、観点カバレッジを一目で分かるようにする。

**`未決定事項管理表.md`**:

  | ID | 論点 | 状態 | 影響範囲 | 関連要件 | 根拠 | 次アクション |
  |---|---|---|---|---|---|---|

- ID は原典にあればそのまま使う。無ければ `D-<domain>-NNN` を採番してよいが、採番したことを明記し、
  事実ではなく本書上の管理IDとして扱う。
- 状態×イベントの抜け（要確認）・各層に出た未確定・暫定決定・着手の妨げになる未検討をここに集約する。

### 6. QA 表の理解補助と回答候補（`90_QA/`）

QA 表（Excel/CSV 等の質問回答シート）への解決可能な参照（相対/絶対パスを伴う出典表記）が
`record_root` 内の既読成果物にある場合のみ適用する。項番付きID（`QA#N`）だけの引用、または
`QA表.xlsx` のようなディレクトリを伴わないファイル名だけの言及では適用しない——いずれも存在場所を
解決できないため。該当する参照が無ければこの節は適用せず、`90_QA/` を作らない。

1. **`90_QA/QA一覧.md`**: QA 表の全項番を次のテーブルで列挙する。原文は要約せず転記する。

     | 項番 | 質問(原文) | 回答(原文) | ステータス | 関連要件 | 関連画面/機能 | 出典シート |
     |---|---|---|---|---|---|---|

   ステータスは「回答済み」「回答候補提示」「要確認（回答候補なし）」の3値。`QA#N` を本設計書内の
   ID として全章から参照できるようにする（`00_設計管理/要件一覧.md` の「関連 QA」列など）。
2. **`90_QA/QA回答補助.md`**: 各項番について次の形で書く（原文回答の有無を問わず、理解補助は毎項目に付す）。
   - **質問の理解補助**: 質問の背景・意図・専門用語の平易な言い換え。なぜこの質問が生じたと考えられるか
     （関連する原典仕様の箇所があれば挙げる）。
   - **原文回答**: あれば転記（要約しない、原文優先）。
   - **回答候補**: 原文回答が無い、または不十分な場合のみ提示。他成果物（要件・設計判断・類似 QA・
     アーキテクチャ決定）から導ける根拠を明記し、複数候補があれば優先順・トレードオフを示す。根拠が
     無ければ「回答候補なし（要確認）」と明記し、捏造しない。
   - **確信度**: 高（原典から明確に導ける）／中（類推が入る）／低（弱い根拠のみ）。
   - **関連**: 関連要件 ID・関連未決定事項 ID（`D-*`）・関連画面/機能。
3. **未決定事項管理表との連携**: 確信度「低」または回答候補なしの項目は `00_設計管理/未決定事項管理表.md`
   にも `D-<domain>-NNN` として登録し、相互参照する（二重管理せず、詳細はどちらか一方に置く）。
4. **反捏造**: 回答候補はあくまで提案であり確定回答ではない。要件一覧・トレーサビリティ等の「確定」情報に
   回答候補を紛れ込ませない。回答候補が後日原典で確定した場合は、次回生成時に「原文回答」へ格上げする。

## graceful degradation

- **未初期化**（active intent が無い＝ record も state も無い）: 「ワークフロー未初期化です。/aidlc を開始してから
  設計書を生成してください。」と表示し、**何も生成せず停止**する。
- **interaction-spec が無い**（非 UI / 早期）: functional-design 由来で状態モデルを導く。導けなければ
  `00_設計管理/状態イベントマトリクス.md` に「UI 状態モデルなし（refined-mockups 未実施）」と明記し、
  要件一覧と各層は可能な範囲で生成する。業務エンティティの状態（状態・ライフサイクル設計）は
  interaction-spec の有無とは独立に、functional-design の状態機械等から可能な範囲で生成を試みる。
- **requirements.md が無い**: その旨を明記し、利用可能な成果物から可能な範囲で生成する。
- **construction 前**: `03_詳細設計/` はコンポーネント種別別に章を残し、確定範囲のみ記載、残りは
  「未検討（確定先: functional-design 3.1 / nfr-design 3.3 / infrastructure-design 3.4 /
  code-generation 3.5）」と書く。`06_インフラ/` は infrastructure-design 待ち、
  非機能要件（A: `02_基本設計/11_非機能要件.md` / C: `02_基本設計/10_非機能要件.md`）も nfr 成果物が
  無ければ各分類を未検討に。状態・ライフサイクル設計（A: `02_基本設計/08_状態・ライフサイクル設計.md` /
  C: `02_基本設計/07_状態・ライフサイクル設計.md`）は functional-design の状態機械が無ければ
  「未検討（確定先: functional-design 3.1）」とする。
- **運用・移行の根拠が無い早期段階**: 運用設計概要（A: `02_基本設計/12_運用設計概要.md` /
  C: `02_基本設計/11_運用設計概要.md`）は operation フェーズ成果物（`<record>/operation/*`）が
  無ければ各章を「未検討（確定先: 運用フェーズ）」とする。移行・リリース方針（A:
  `02_基本設計/13_移行・リリース方針.md` / C: `02_基本設計/12_移行・リリース方針.md`）は
  build-and-test / ci-pipeline 成果物が無ければ
  「未検討（確定先: build-and-test 3.6 / ci-pipeline 3.7）」とする。いずれも見出しは削除しない。
- **選んだアーキタイプの骨格に含まれる章で、案件に該当しないもの**（例: アプリ系でバッチが無い）:
  そのファイル/章は削除せず「対象外（理由）」と書き、未検討と区別する。骨格に**含まれない**章
  （例: インフラ系の画面設計）は作らない。
- **QA 表への解決可能な参照が無い**: `90_QA/` を作らない（他の骨格外の付録と同様、対象外ではなく
  「そもそも生成しない」扱い）。
- 部分的なプロジェクトでも、**選んだアーキタイプの骨格と標準章立ての形**を必ず出す（内容が無い章は
  削除せず「未検討」を残し、`00_設計管理/未検討一覧.md` に集約する）。これが本設計書の「抜け漏れ可視化」の要。
